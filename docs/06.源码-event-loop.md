# 总揽
一个EventLoop 大概有4个核心元素:
1. thread， 一个 EventLoop 其实内部只对应一个 thread
2. executor, 这是一个单线程的线程池，它内部的线程其实就是上面的 thread
3. taskQueue，缓存还未执行的任务
4. scheduledTaskQueue, 处理定时任务的队列
5. selector，这个selector 是在 EventLoop 的构造函数里实现的。

所以，一个 EventLoop，即处理IO任务，又处理定时和普通任务。

# 两个 Selector
一个比较异常的现象是，一个EventLoop 内部，其实是有两个 selector 引用的:
```java
public class NioEventLoop{
    private Selector selector;
    private Selector unwrapedSelector;
}
```
其实它们本质上是一个，区别在于，Selector 有一个存储 SelectedKey 的容器字段，官方Selector的实现是使用Set 实现的，它的遍历性能不好，也就是 unwrapedSelector
作者通过反射使用一个数组替换Set，从而追求更好的遍历性能，这就是 selector。

# EventLoop 何时启动？
在首次调用 eventLoop的 execute 方法时，内部会检查 eventloop.thread 是否为空，如果是，则向 executor 提交一个任务。
这个任务内部，首先将 eventLoop.thread 赋值为 executor 的执行线程，然后开始一个 evnetLoop 死循环：不断找 IO / 普通任务 / 定时任务

# 提交任务会唤醒EventLoop吗？
会的。提交任务时，会通过 selector.wakeup() 来唤醒它。

猜测一下底层原理， 有两种方案：
第一个是通过向 epoll 发送信号。来唤醒。
第二个是通过注册一个专门的唤醒fd, 这个 fd 写入数据来唤醒。

除此之外，EventLoop 内部的 selector 的 select 方法是有超时参数的版本，
即使一直没有任务到来，也会定期唤醒线程。

# 唤醒EventLoop的细节
试想，高并发情况下，多个线程同时执行 selector.wakeup，这是一个重量级的操作，但其实只需要保证一个线程调用 wakeup 就够了。
为了实现这个需求，需要使用 CAS： 设置一个变量 boolean wakeup = false ，把它给 CAS 成 true，CAS成功的那个线程才执行 wakeup

# 何时会进入Select阻塞，阻塞多久？
当没有任务时，才会进入阻塞状态。

在没有定时任务时，阻塞时间是1秒，有定时任务时，阻塞时长大约是 【定时任务超时时间点 - 当前时间点】

# 关键参数：ioRatio
EventLoop，既要处理io事件，又要处理普通的任务， ioRatio 这个参数则用来控制处理各种事件的比例，它的范围是 1 ~ 100。

当 ioRatio 是100时，并不意味着完全不处理普通任务，而是： 一口气执行完所有的IO任务，然后一口气执行完所有的普通任务。

通常情况下，先一口气执行完所有的IO任务，记录IO任务的耗时为 ioTime， 然后 通过 ioTime * (1 - ioRatio) / ioRatio 来计算出普通任务的耗时，
然后按照这个耗时来运行普通任务。

需要注意的是，这里的“一口气执行完所有的IO任务”，实际上就是通过 前面说的那个优化后的数组 进行遍历的。

# accept 事件发生后，eventLoop 做了什么？
首先，创建一个java原生的 SocketChannel,然后在它的基础上，创建 NIOSocketChannel，然后，用它作为参数，启动NioServerSocketChannel的
pipeline 上挂在的 handler的 channelRead 回调，（回忆，此时有3个Handler，依次是 head -> acceptor -> tail)
显然 acceptor 上的 channelRead 才是最关键的。

acceptor 内部，会提交一个任务给 childGroup 的 EventLoop，这个 EventLoop 会执行这个任务。
这个任务内部，将新建的 NioSocketChannel 注册到 EvnetLoop 自己的 Selector，然后触发用户注册的初始化器，
初始化器内部会将用户指定的Handler 添加到 NioSocketChannel 的 pipeline 上。
最后，注册 NioSocketChannel 感兴趣的事件是读事件。
