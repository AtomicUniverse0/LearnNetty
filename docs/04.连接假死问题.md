# 出现原因
* 网络设备出现故障，例如网卡，机房等，导致底层的TCP连接已经断开
* 网络环境不好，丢包频繁，导致客户端数据发布到服务端
* 应用程序线程阻塞，无法进行读写

# 不良影响
* 空占用服务端的资源
* 对假死的连接发松数据，得到的反应是连接超时

# 一个深入的问题
在 Netty中，有一个 quitHandler:
```java
@ChannelHandler.Sharable
@Slf4j
public class QuitHandler extends ChannelInboundHandlerAdapter {
    @Override
    public void channelInactive(ChannelHandlerContext ctx) throws Exception {
        // 取消服务端注册的 channel
        SessionFactory.getSession().unbind(ctx.channel());
        log.info("已经断开连接");
    }

    @Override
    public void exceptionCaught(ChannelHandlerContext ctx, Throwable cause) throws Exception {
        SessionFactory.getSession().unbind(ctx.channel());
        log.info("已经异常断开连接");
    }
}
```

它会在连接断开时触发，为何连接假死不会导致上述回调被触发？

我大概想明白了：连接断开是需要收到 FIN 报文的，netty 底层多半是通过 read 返回 -1 来确定对方关闭连接
然后才会触发 QuitHandler 的若干回调
